# 040-261105 회사 분석(AI 연동/에이전트 + RAG) — 기획·설계 분석 (초안)

## 개요
- **1차 목표**: 수집 데이터 기반 **회사 분석** + 분석 내용을 **마크다운 메모로 작성**(에이전트 활용).
- **의의(AI 연동)**: 누적 공고/회사 데이터를 **근거**로 요약·비교·메모를 생성. 단, **수치 정확성(집계)**과 **근거 해석(RAG/LLM)**을 분리해 신뢰성을 확보한다.
- **현황(기존 자산)**: `job_postings`(company/position/career/tech/location/deadline/site/crawled_at/dedup_key 등), 회사 메모 `company_notes.note_md`/태그·북마크·별점(031), 블랙리스트/평점 연계. DB `scraper_platform`.
- **작성일**: 2026-11-05 / **상태**: 기획·설계 분석 중(구현 보류, 정리 후 진행)

## 1. 문제/질문 유형 분석 (핵심 분리)
| 사용자 질문 예 | 필요한 처리 | LLM/RAG | 비고 |
|---|---|---|---|
| “이너인포 최근 공고 언제?” | DB 조회 `MAX(crawled_at)`/최근행 | 불필요 | 결정론적·즉시 |
| “요즘 공고 많이 나옴?” | DB 집계(기간별 `COUNT`, 전기 대비, 직군/회사 분포) | 불필요(선택: 수치 요약만) | **통계=집계**(통계 페이지 UI와 별개 개념) |
| “최근 늘어난 공고 공통 요구/특징?” | 집계 수치 + 관련 공고 **근거 검색** → 요약 | RAG+LLM | 수치=쿼리, 해석=근거 인용 |
| “A사 vs B사 공고 비교(근거)” | 회사별 근거 공고 검색 → 비교 생성 | RAG+LLM | 공고 id/url 출처 필수 |
| “이 회사 분석 메모 써줘” | 집계+근거 샘플 → MD 초안 생성/갱신 | 에이전트(+RAG) | `company_notes.note_md`(031) 저장 |

**결론**: RAG는 “현 데이터를 대신 계산”하는 게 아니라, **근거 문서를 찾아 LLM이 설명/생성**하는 것. 통계 수치는 항상 DB 결과가 진실(source of truth).

## 2. 목표와 비목표
- **목표(MVP 후보)**: 회사 단위 분석 — (a) 사실/추이 집계 근거 확보, (b) 근거 포함 회사 분석 **MD 초안** 생성→`note_md` 반영.
- **비목표(초기)**: 전체 통계 대시보드 UI 구축, 상시 대화형 에이전트 상주, 로컬 대형모델 운영, 수치를 LLM이 “추정”하는 방식.

## 3. 설계 방향(안)
### 3.1 구성 요소
- **(A) 집계(결정론)**: 회사/기간 기준 최근공고일·기간별 count·분포. LLM 미사용. (API/내부 서비스 형태는 구현 시 확정; UI=통계 페이지와 분리 가능)
- **(B) 근거 검색(RAG, Phase2)**: 공고 단위(확장 시 섹션) 청킹+메타(`posting_id,company,site,position,career,tech,location,deadline,crawled_at,source_url`) → 임베딩 → **하이브리드**(메타필터+키워드+벡터) 검색. 인용 필수.
- **(C) 분석 에이전트(메모)**: A의 수치 + (B 또는 샘플 근거) → MD 초안 생성. frontmatter/본문에 `generated_at, 기준기간, 집계수치, 근거 posting_ids/urls` 기록 → 031 저장/렌더. 근거 없으면 단정 금지.

### 3.2 데이터·하드코딩 원칙(프로젝트 규칙)
- 직무/지역/스택/분류·태그 등 **기준값은 DB 코드화+조회/검색 API**(프론트/백 `if/map` 하드코딩 금지). LLM 추출값도 코드 테이블로 정규화/매핑.
- 신규 기준 데이터: DDL(`docs/.../ddl-*vN.sql`, 멱등 시드) + Entity/Repo + 조회 API + (필요 시) 배포 워크플로 DDL 라인.

## 4. AI 연동·연결 파이프라인(결정 반영)
| 방식 | 토큰비 | 자원/운영 | 적합도 |
|---|---|---|---|
| DB 집계(A) | 0 | 기존 DB | **항상**(사실/통계) |
| **클라우드 LLM/임베딩 API**(서버가 HTTP 호출) | 무료 티어/크레딧(한도·정책 변동) 또는 종량제 | 서버 가벼움, **API 키 필요** | MVP 권장 |
| 로컬 모델(Ollama 등) | 0 | CPU/RAM(/GPU) 부담, 8080/8081/8082 경합 | MVP 비권장, 분리 시 검토 |

- **주의**: ChatGPT/Gemini/Copilot **웹/앱 사용 ≠ 서버용 개발자 API**(세션 재사용 불가). API는 별도 키·과금/한도 체계. (예: Gemini API는 별도 무료 티어가 있을 수 있으나 한도/데이터 정책 확인 필요)
- **연결 관리(확정 방향)**: **관리자용 공용 연결 파이프라인**을 서비스에 둔다(재배포 없이 모델/연동 교체). 제공자·모델ID·Base URL·출력토큰상한·활성/우선순위(폴백) 등을 관리자만 설정.
  - **키/비밀**: `.env` 평문 상시관리 대신 **DB 암호화 저장**(조회 마스킹·원문 재노출 금지) + 변경 감사로그. **`.env`는 부트스트랩/폴백**(초기 1회 이관 또는 장애 시 대체)으로만 사용. 키/설정 코드·커밋·채팅 노출 금지.
  - **사용자별 BYO 키는 후순위**(별도 과제): 공용 파이프라인 안정화 후, “개인 키 사용” 요구 시 라우팅 규칙(기본=공용, 개인키 시 개인)과 키 암호화/권한을 함께 설계.
  - **하드코딩 금지**: provider/model/옵션은 설정값(필요 시 코드 테이블)으로 관리.

## 5. 운영/아키텍처 (MVP 가정)
- MVP: 기존 인프라 내 **저빈도 배치/온디맨드**(기존 서비스와 자원 경합 방지). **관리자 연결 파이프라인(Phase 0)** → 회사 분석 MD 초안(Phase 1) 순. 신규 상시 서비스/포트는 필요 시에만, `infra/services.yml` SSOT 준수.
- 확장: 사용자별 BYO(후순위), RAG 상시화·대용량 인덱싱·로컬모델 필요 시 **워커/전용 분리** 검토.

## 6. 안전장치·평가
- 프롬프트: “근거 없는 생성 금지, 출처 id/url 인용, 불확실/없음 명시”. 통계 수치는 쿼리값만 사용.
- 루프/타임아웃 제한, 비용·토큰·지연·실패 로깅(연결/모델별). 재크롤링 시 재색인 정합성.
- 키/연결 보안: 관리자 전용 설정, 키 암호화·마스킹, 변경 감사로그, 무료티어 한도/데이터정책 주의.
- 평가(Phase2): 골든 Q&A·근거율(인용 일치)·태깅 샘플 정확도.
