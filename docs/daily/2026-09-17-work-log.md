## 이슈 및 해결
- [백업 cron 3일 연속 미실행]: cron.d 파일 내용 정상(CRON_TZ=Asia/Seoul, 30 3/35 3). 산출물 디렉토리·실행 로그 전무 → cron 데몬 미기동 유력. SSH 확인 명령어는 향후 작업 참조.
- [원인 확정]: `systemctl status cron` → `Unit cron.service could not be found` — cron 패키지 자체가 미설치. 9/15~9/17 백업이 한 번도 실행 안 된 이유. 수정: `sudo apt install -y cron` + `systemctl enable --now cron` 후 수동 1회 실행으로 검증 예정.
- [portfolio_platform 원인 확정]: 2026-08-21 인프라 정리에서 의도적 DROP. 9/14에 Grants 잔재를 보고 착각해 백업 대상에 추가한 것. DB 생성 대신 백업 목록에서 제외함. 앱 코드에서 참조 없음 확인.
- [99-binlog.cnf 위치 정정]: 웹 서버가 아니라 **DB 서버(161.33.138.23)**의 `/etc/mysql/mariadb.conf.d/`에 있어야 함. 런타임은 14일로 적용済(9/14 SET GLOBAL). 파일 영속화 + 재시작은 DB 서버에서 처리 필요.
- [99-binlog.cnf 기록 완료]: DB 서버에 파일 작성됨 (`[mariadb]` + `binlog_expire_logs_seconds=1209600` 확인). 남은 것은 MariaDB 재시작(적용) + 복구 확인.
- [binlog 영속화 완료]: 재시작 전후 모두 1209600 유지 → 파일 적용 성공. 전 서비스 헬스체크 정상(platform 200/auth 200/scraper 401/resume 200). 남은 확인: `SHOW MASTER STATUS` 출력 (붙여넣기 누락).
- [log_bin=OFF 발견]: 재시작 후 `log_bin OFF` 확인. MariaDB 기본값이 OFF이므로 영속 설정 없이는 켜지지 않음. 기존 `[coordinate OK]`는 빈 출력에도 exit 0이라 false positive였을 가능성 — 실제 좌표があったか 의문. 수정: 99-binlog.cnf에 `log_bin`+`server_id` 명시 + 워크플로우 진단의 빈 출력 판정 수정.
- [binlog 최초 활성화 성공]: 기존 binlog 파일 없음 → 과거에 켜진 적 없음 확정(9/13 기록설·coordinate OK 모두 오인). `log_bin=mysql-bin`+`server_id=1`+재시작 → `log_bin=ON`, `mysql-bin.000001 pos 328` 실좌표 확인. PITR 체인은 이 시점부터 시작. 전 서비스 복구 확인.
